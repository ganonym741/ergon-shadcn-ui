# Maintainer guide

## Commit and push

Root `bun install` enables Husky. lint-staged runs ESLint on staged JavaScript/TypeScript first, then formats supported files with Prettier only if linting passes. Commit messages are validated with commitlint. Use `type(scope): description`, for example `feat(table-plus): add nested row actions`, or stage your changes and run `bun run commit` for the Commitizen prompt. Standard Conventional Commits types and optional scopes are supported.

Pushes run `bun run verify`: ESLint, formatting checks, app and CLI TypeScript checks, both test suites, and the production build. Install the CLI dependencies with `bun install --cwd packages/cli --frozen-lockfile` first. These hooks are contributor tooling; installed components and the published CLI do not depend on them.

Run `bun run hooks:check` after editing hook configuration. It tests real commits and pushes in an isolated repository under ignored `output/`, including invalid messages, failed checks, and preservation of partially staged edits.

## Develop the CLI

The documentation app and CLI have separate dependencies:

```sh
bun install --cwd packages/cli --frozen-lockfile
bun run cli:check
bun run cli:test
bun run cli:build
```

The starter in `templates/react-vite` is bundled into the CLI during build. Component source is distributed through the registry generated by `scripts/build-registry.ts`.

## Deploy the registry

Run `bun run build` and publish `dist`. [netlify.toml](../netlify.toml) defines Netlify's build settings and `REGISTRY_URL`. Change that URL when using a different public host.

Deploy the intended source revision and check its component URLs return JSON before releasing a CLI that depends on those entries.

## Automatic npm releases

[Publish CLI to npm](../.github/workflows/publish-npm.yml) runs after every push to `main`, including merged pull requests. It validates the app and CLI, then publishes `@ergonui/cli` through npm trusted publishing. The private repository root is never published.

Versions advance automatically by patch from the highest published stable version. A higher stable version declared in `packages/cli/package.json` starts a new minor or major release; refresh its Bun lockfile when changing that baseline. Version changes happen only in CI packaging, without release commits. The CLI's `--version` and help output use the packaged version. Re-running an already published commit skips publication. Runs queue serially rather than replacing pending releases.

One-time npm setup: open the settings for `@ergonui/cli`, add a **GitHub Actions trusted publisher**, and enter:

| Field             | Value                |
| ----------------- | -------------------- |
| Owner             | `ganonym741`         |
| Repository        | `ergon-shadcn-ui`    |
| Workflow filename | `publish-npm.yml`    |
| Environment       | Leave blank          |
| Allowed action    | Direct `npm publish` |

No npm token secret is needed. Save this configuration before merging the workflow. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) for the account setup. The workflow uses GitHub-hosted runners, Node 24, npm 11.21.1 and OIDC; repository write permission is not required.

The workflow can also be run manually on `main` to retry a failed release. Netlify registry deployment remains separate: deploy the intended component registry revision before releasing CLI features that depend on new entries.

## Manual CLI release

Publishing requires access to the `@ergonui` npm scope and npm's publishing authentication. Version the CLI independently from the documentation app; published versions cannot be replaced.

1. Update `packages/cli/package.json` to the next version.
2. Refresh the lockfile, validate, and pack:

   ```sh
   cd packages/cli
   bun install
   bun run check
   bun run test
   npm pack --pack-destination ../../output
   ```

3. Test the tarball in a clean application, including a production build.
4. Authenticate and publish from `packages/cli`:

   ```sh
   npm login
   npm whoami
   npm publish --access public
   ```

The repository root is private. The CLI package includes its executable, starter, README, license, and package metadata; `prepack` builds the executable and starter.

For releases requiring approval, use [npm staged publishing](https://docs.npmjs.com/cli/v11/commands/npm-stage/). A staged version reserves its version number; approve it rather than publishing the same version again.

After release, test the published CLI with each documented package runner, including a clean application build with its selected package manager. A CLI README change reaches npm with the next package release.
